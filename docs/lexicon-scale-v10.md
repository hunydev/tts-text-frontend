# 사전 크기별 런타임 점검

2026-09-16에 이 VM에서 수행한 합성 데이터 실험이다. 발음 품질 평가나 서비스
성능 보증 수치가 아니다. 외부 사전을 가져오지 않고 서로 다른 ASCII 키를
만들어 조회 가능성과 비용을 확인했다.

## 발견한 병목과 변경

이전 `ttf_rule_match`는 토큰을 처리할 때 전체 resource hash table을 순회하며
`exact`/`pattern` 종류인지 검사했다. 따라서 발음 사전만 커져도 TN 규칙 검색이
느려졌다. freeze 단계에서 실제 TN 규칙만 연결한 불변 인덱스를 만들고,
정규화 중에는 그 인덱스만 순회하도록 변경했다.

boundary cue 인덱스 생성도 `identifier_label` 또는 `context_cue`인지 먼저
확인한 뒤 유효한 override를 조회한다. 발음 항목마다 불필요하게 유효값을
다시 조회하던 작업을 줄였다. 기존의 resource hash storage와 public ABI는
유지했다. layer, exact 우선, longest match, specificity, 선언 순서에 의한
우선순위 비교도 유지했다.

## 실험 조건

- Linux 6.12.93 x86_64, glibc 2.39, AMD EPYC 9554P, Python 3.12.3
- GCC Release shared library를 `tools/web/native.py`의 ctypes 정의로 직접 호출
- 기존 시스템 리소스 위에 customer layer TSV 1,000 / 10,000 / 50,000행 추가
- 각 크기마다 engine create, 추가 resource load, freeze 시간을 분리
- 입력 키: `lexscale` 뒤에 인덱스의 고정 6자리 base-26 소문자 표현
- 발음 값: `사전` 뒤에 인덱스의 고정 5자리 한글 표현. 문자를
  `가나다라마바사아자차카타파하`에서 골라 생성하여 모든 값이 서로 다르도록 함
- 입력 문장: `<key>를 확인합니다. `, 기대 문자열: `<value>를 확인합니다. `
- 전체 키를 500문장씩 정규화하여 출력 전체와 customer 발음 span 수 확인
- 별도 고정 부하: 사전 전체에서 균등하게 뽑은 1,000키를 한 번에 정규화,
  5회 측정의 중앙값 사용
- 표의 정규화 시간은 `ttf_normalize` 호출 시간이며 Python의 문자열 생성,
  출력 비교 및 span 검사 시간은 제외. native 내부 메모리 할당은 포함
- 같은 VM에서 다른 개발 작업도 진행되어 CPU를 독점하지 않았다. 변경 전후
  작업 중의 시스템 사전을 사용했으므로 엄밀히 고정된 출시 성능 시험은 아님

사용한 바이너리 SHA-256:

## 남은 storage 한계

현재 resource hash table은 **1,021 bucket 고정 크기**이고 충돌은 연결 리스트로
처리한다. 합성 사전 키만 현재 FNV-1a bucket 계산에 넣은 결과는 다음과 같다.
기존 시스템 리소스는 이 표의 길이 계산에서 제외했다.

| 키 수 | 사용한 bucket | bucket당 평균 키 | 가장 긴 연결 리스트 | TSV 크기 |
| ---: | ---: | ---: | ---: | ---: |
| 1,000 | 622 | 0.979 | 4 | 57,000 bytes |
| 10,000 | 1,021 | 9.794 | 17 | 570,000 bytes |
| 50,000 | 1,021 | 48.972 | 62 | 2,850,000 bytes |

TN의 전체 사전 순회는 제거했지만, 직접 조회하는 hash chain은 여전히 사전
크기에 따라 길어진다. 한 종류의 합성 키 실험은 충돌 공격, 모든 실사용 키
분포, multiword 집중 prefix, 100만 항목의 메모리 비용을 검증하지 않는다.
다음 성능 작업은 발음 사전의 크기에 맞게 확장되는 hash/trie storage,
공유 prefix가 많은 multiword 사전, 실제 문장 분포에서의 p50/p95 및 메모리
측정이다. API와 storage를 분리한 채 진행할 수 있다.

## 회귀 검증

`tests/unit/test_rule_index.c`는 10,000개 합성 발음 항목과 함께 규칙의 layer,
exact 우선, 길이, specificity, 선언 순서, 단어 경계, 언어 필터, 반복 freeze,
실제 발음 사전 조회를 검증한다. 실행 시간 임계값은 테스트에 넣지 않았다.
느린 CI VM에서 발생하는 성능 편차를 기능 실패로 오인하지 않기 위해서다.

별도로 authoring compiler의 허용 키와 native classifier의 인식 범위를
대조했다. 기존 grammar에서는 `a1b`, `a1b2`, `a-1b`, 임의의 `foo++`를 허용해도
전체 단어가 조회되지 않았다. `3D`와 `3d` 또한 semantic term의 대소문자 처리
차이가 있었다. 이 결과를 authoring 허용 형태와 semantic term 리소스를
정비하는 작업에 전달했다. 단순히 TSV에 행이 있다는 사실만으로 그 발음을
실제 입력에서 조회할 수 있다고 판단하면 안 된다.
