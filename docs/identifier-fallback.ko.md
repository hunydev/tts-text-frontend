# 식별번호 대체 읽기와 하이픈 정책

2026-09-28. 사용자 결정에 따른 두 가지 변경을 다룬다.

1. **speech 출력에서 거부된 숫자열 읽기.** 전화번호·범위 인식기가 모두 거부한
   순수 숫자·하이픈 열(`33-54-385734-21`, `110-234-456789`)을 원문 그대로 내보내지
   않고 식별번호로 한 자리씩 읽는다.
2. **식별번호 하이픈은 `다시`.** `identifier_render / ko-KR / separator` 기본값을
   공백에서 ` 다시 `로 바꾼다. 라벨 있는 식별번호도 같이 바뀐다.

## 왜

AI Hub 159 제공 참조에서, 엔진이 원문 그대로 내보내 틀린 문장 4,483건 중 약 70%가
하이픈으로 이은 숫자열이었다 (면허·사업자·주문번호). 참조는 이 모양을 2·3묶음에서
98~99% 한 자리씩 읽는다. speech 출력은 TTS가 읽을 텍스트인데 `33-54-385734-21`이
날것으로 가는 것은 원하는 동작이 아니다.

하이픈 읽기는 참조도 갈린다. 식별번호 모양에서 `다시`가 가장 많다 (2묶음 44%, 3묶음 39%,
4묶음 68%). 과반은 아니므로 리소스로 바꿀 수 있게 둔다.

## 동작

| 입력 | speech | text |
|---|---|---|
| `33-54-385734-21번으로` | 삼삼 다시 오사 다시 삼팔오칠삼사 다시 이일번으로 | 원문 그대로 |
| `110-234-456789를` | 일일공 다시 이삼사 다시 사오육칠팔구를 | 원문 그대로 |
| `사업자번호 110-234-456789` | 사업자번호 일일공 다시 이삼사 다시 사오육칠팔구 | 같음 |
| `Call 110-234-456789 now.` (en-US) | Call one one zero two three four … now. | 원문 그대로 |

- **IR은 바꾸지 않는다.** 대체 읽기 구간은 인식기 판정 그대로 `TEXT` /
  `syntax.invalid-phone` 또는 `syntax.invalid-range`다. trace에
  `identifier-fallback / rejected-numeric-read-as-identifier` 결정이 남는다.
- 코어는 언어 독립이다. 구간을 `DIGIT_SEQUENCE / financial_identifier`로 렌더러에
  넘기므로 각 언어 팩이 자기 식별번호 문법으로 읽는다. 영어는 0을 `zero`, 하이픈을
  공백으로 읽는다.
- `--unreadable preserve|drop|read` 어느 설정에서도 같이 읽는다. 읽을 수 없는 문자가
  아니라 인식된 식별번호 모양이기 때문이다.

### 대체 읽기를 하지 않는 것

| 경우 | 이유 |
|---|---|
| text 출력 | `docs/api.md`의 원문 보존 계약 |
| 전화번호 모양 (첫 묶음 `0X`/`0XX`) | 형식이 틀린 전화번호는 기존 계약대로 보존한다 (`phone-cue-v21-cue-malformed-long`, `phone_number_tail` overlay) |
| 유효한 전화번호·범위·날짜 | 자기 문법으로 이미 읽힌다 |
| 영숫자 코드 (`26-6573557-L97`, `32124a`) | 다음 규칙군. 이번 범위 아님 |
| 거부 사유가 다른 것 (`2026-02-30` 등) | `syntax.invalid-phone`, `syntax.invalid-range`만 대상 |

## 리소스

```
identifier_render	ko-KR	separator	 다시 
```

전화번호 하이픈은 `phone_render / separator`로 따로 정하며 영향을 받지 않는다.
고객·사용자 overlay로 `identifier_render separator`를 공백으로 되돌리면 라벨 식별번호와
대체 읽기가 모두 공백 구분으로 읽힌다. 대체 읽기 자체는 그대로 동작한다.

## 바뀐 기존 계약

`contract_diff`로 `tests/evaluation/*.jsonl` 전부를 변경 전·후 엔진에 돌렸다. 출력이
바뀐 행은 **10행이고 전부 하이픈 자리의 `다시`뿐**이었다. 다른 변화는 0건이다.
행마다 이전·이후와 근거를 [정책 원장](audit/identifier-separator-policy-20260928.json)에
남겼다. 하드코딩된 기대값 4곳(`test_identifiers.py`, `test_phone_contracts.py`,
`test_semantic_boundaries.c`, 문서 2곳)도 원장에 있다.

### 참조 검사 `korean-range-again` 조정

이 검사는 숫자 범위를 `다시`로 읽은 참조를 오류로 본다. 겉모양 `숫자-숫자`만 보고
판단해서 식별번호(`접수 번호는 123-456`)까지 잡았다. 기존 `@address` 예외와 같은
원칙으로 다듬었다: **계약이 그 구간을 `DIGIT_SEQUENCE / financial_identifier`로
명시한 경우만** 뺀다. 선언이 없거나, id·카테고리에 range가 있거나, 일부 구간만
식별번호이거나, 다른 단위이면 계속 잡는다 (self-test 5건). 선언이 없던
`domain_cases*.jsonl` 2행에는 엔진이 실제로 내는 식별번호 IR을 선언했다.
