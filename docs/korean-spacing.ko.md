# 한국어 TN 띄어쓰기 정책과 공백 진단

2026-09-28. 범위: 한국어 수 읽기의 만 단위 경계, 공백 차이의 유형별 진단.
음성 합성이나 청취 평가는 하지 않는다. 공백이 실제 TTS의 휴지 길이를 보장하지는 않는다.

## 기본 출력 기준

[국립국어원 한글 맞춤법 제44항](https://www.korean.go.kr/kornorms/m/m_regltn.do?regltn_code=0001)은
수를 한글로 적을 때 만 단위로 구분한다. 이 프로젝트의 TTS용 정규화 출력도
그 경계를 사용한다. 일반 금융 문서에서 변조 방지를 위해 금액을 붙여 쓰는 관행은
문서 표기 목적이며, TTS의 기본 출력 정책과 구분한다.

| 입력 | 기본 출력 |
|---|---|
| `12,500원` | `만 이천오백 원` |
| `1억2천3백만원` | `일억 이천삼백만 원` |
| `100000001` | `일억 일` |
| `1~1.5만 원` | `만 원에서 만 오천 원` |

0인 묶음을 건너뛰어도 앞뒤에 불필요한 공백을 만들지 않는다. 한 묶음 안의
`이천오백`, `십이`, 고유어 `열두`, 단어 `유월·시월`을 임의로 나누지 않는다.
번호 자릿수 사이 공백과 약어 읽기 간격은 별도 발화 정책이다.
조사, 리터럴 별칭, 원래 한글 문장, 보호 구간, 영어 출력에 일괄 문자열 치환을 하지 않는다.
Korean pack의 cardinal verbalizer가 Semantic IR 숫자 값을 읽을 때 경계를 생성한다.
숫자 값·단위·의미 분류·원문 byte 좌표는 유지한다.

제43항의 단위 명사 띄어쓰기는 추가 개선 후보지만 문맥 검토가 필요하다.
예를 들어 순서를 나타내는 표현에는 붙여 쓰기가 허용되며, 합성어의 뜻도 구분해야 한다.
[국립국어원 ‘일 등/일등’ 설명](https://www.korean.go.kr/front/mcfaq/mcfaqView.do?mcfaq_seq=9165&mn_id=217)을
참고한다. 따라서 모든 수와 뒤 한글 사이에 공백을 넣는 규칙은 사용하지 않는다.

## 선택 옵션: 읽기 단위 띄어쓰기 (2026-09-29)

AI Hub 159 참조는 맞춤법(만 단위)이 아니라 **읽는 단위마다** 띄운다. 3~5자리 한자어 수에서
경계가 있는 참조는 사실상 전부 단위마다 띄웠고(`만 구천 사백 사십 원`, `삼백 일 호`),
한 자리씩 읽는 전화번호도 71%가 `공 일 공`처럼 한 글자씩 띄웠다. TTS 모델이 이런 텍스트로
학습되었다면 띄어쓰기가 끊어 읽기 단서가 되므로, 이 관행을 **고객 overlay로 선택**한다.
기본값은 계속 제44항이다. 어느 쪽을 쓸지는 대상 TTS 모델의 학습 텍스트와 청취로 정한다.

`resources/customers/reading-unit-spacing/ko-KR/rules.tsv`:

```tsv
number_spacing	ko-KR	group	unit
number_spacing	ko-KR	digits	spaced
```

| 입력 | 기본 (제44항) | 읽기 단위 |
|---|---|---|
| `19440원` | `만 구천사백사십 원` | `만 구천 사백 사십 원` |
| `2018년에` | `이천십팔 년에` | `이천 십 팔 년에` |
| `72.5km` | `칠십이 점 오 킬로미터` | `칠십 이 점 오 킬로미터` |
| `010-1234-5678` | `공일공 일이삼사 오육칠팔` | `공 일 공 일 이 삼 사 오 육 칠 팔` |
| `K37PA1798` | `케이 삼칠 피에이 일칠구팔` | `케이 삼 칠 피 에이 일 칠 구 팔` |

`group unit`은 한자어 수의 모든 단위(십·백·천과 만·억…) 뒤에 공백을 넣는다. `digits spaced`는
한 자리씩 읽는 번호(전화, 식별번호, 카드번호, 선행 0, 소수부)의 숫자·글자를 한 단어씩 쓴다.
고유어 수사(`스물다섯 개`)와 단어(`유월`), 고정 이름(`코로나 일구`)은 바꾸지 않는다.
CLI `--customer`, 웹 고객 overlay, 평가기 `--overlay`로 적용한다.
계약: `tests/evaluation/ko_reading_unit_spacing_v23.jsonl`.

## 사람이 편집하는 리소스

### 나이·차수·학년의 단위 경계

`15세인 → 십오 세인`, `1차 예약 → 일 차 예약`, `3학년에 → 삼 학년에`는
수사 내부를 나누는 변경이 아니다. 숫자와 단위 명사를 별도로 인식하는 규칙이다.
`languages/ko-KR/counters.c`가 기존 숫자 스캐너와 COUNTER/RANGE IR을 재사용하고,
`rules/counters.tsv`의 `counter_noun_unit`으로 단위를 선언한다. `counter` 행이
한자어/고유어 수사 읽기를 결정한다. 현재 세·차·학년은 한자어 수사다.

단위 뒤의 전체 Hangul token이 `particle` 또는 `counter_noun_tail`에 일치해야 한다.
`인`, `이신`, `미만` 등의 정확한 꼬리를 선언하며 임의 접두사로 나누지 않는다.
따라서 `3세대`, `3차원`, `6학년제`, `15세탁기`는 이 규칙으로 쪼개지 않는다.
원래 한글 `십오세`를 교정하는 전역 맞춤법 검사기가 아니다. 숫자 표기 입력에만
적용하며, 정수·선행 0 수량·전각 숫자·단위가 있는 범위를 지원한다.
소수/음수의 새 counted-noun 문법은 이번 범위에 포함하지 않는다.

```tsv
counter_noun_unit	ko-KR	세	1
counter	ko-KR	세	sino
counter_noun_tail	ko-KR	인	1
```

고객 TSV에서 unit flag를 `0`으로 두면 그 단위를 비활성화한다. 새 꼬리를 추가할 때
같은 글자로 시작하는 일반 단어를 부정 계약에 반드시 넣는다. 플래그는 `0|1`, 키는
기존 bounded key 검사(32바이트 미만)를 따른다. 단위 table을 단순 공백 치환에 쓰지 않는다.
`counter_noun_attached / 차 = 1`은 숫자에 붙은 차수만 허용한다. 공백으로 분리된
`0987 차는`의 차는 차량 등 일반 명사일 수 있으므로 앞 번호를 기수로 바꾸지 않는다.

범위를 새로 인식하면 기존 수량 범위 정책에 따라 양쪽 단위를 읽는다:
`15~19세 → 십오 세에서 십구 세`. 참조가 `십오에서 십구 세`라면 의미가 같아도
공백 제거 점수에서 다르며 원래 점수에 그대로 반영한다. 고객이 끝 단위만 원하면
기존 `range_repeat_unit / ko-KR / 세 = 0`을 선택할 수 있다. 읽기 정책 차이를
맞춤법 오류로 묶거나 평가에서 숨기지 않는다.

나이·생년월일 참조에는 `십 오`, `십 일`처럼 수사 내부를 띄운 표기가 매우 많다.
단위 누락을 수정해도 이 부분은 정확 일치에서 계속 차이로 남는다. `코로나19`의
`십구/일구`는 고유 명칭의 읽기 문제로 별도 사전 검토 대상이다. 필요할 때
`[[코로나19]]{코로나 일구}`를 쓰면 되며, 모든 한글+숫자를 자리 읽기로 바꾸지 않는다.
제공 참조·기존 정확/공백 제거 지표는 수정하거나 사례를 제외하지 않는다.

### 수 묶음 정책

`resources/languages/ko-KR/rules/numeric.tsv`:

```tsv
number_spacing	ko-KR	group	space
```

값은 `space` 또는 `compact`다. 이전처럼 수 묶음 사이를 붙여 읽도록 선택하려면
Customer TSV에 같은 키를 `compact`로 선언한다. Domain/Customer 우선순위는 기존과 같다.
해당 행이 없는 과거 resource root는 `compact`로 동작한다. C ABI나 전역 옵션은 추가하지 않았다.

```sh
printf 'number_spacing\tko-KR\tgroup\tcompact\n' > /tmp/ttf-spacing.tsv
build/ttf validate-resource --resources resources /tmp/ttf-spacing.tsv
build/ttf normalize --resources resources --customer /tmp/ttf-spacing.tsv '12,500원'
# 만이천오백 원
```

웹의 고객 TSV 칸에서도 적용할 수 있다. 발화용 세부 간격 프로필이 필요하면
이 정책과 구분해서 계약을 먼저 작성한다. 참조가 `십 이`라고 되어 있다는 이유만으로
기본값을 바꾸거나 이를 독립적인 맞춤법 정답으로 승인하지 않는다.

## 공백 차이의 진단

`benchmark/evaluators/spacing_audit.py`는 이미 완료된 보고서만 읽는다.
공백 이외의 글자가 완전히 같은 문장에 한해, 공백 위치를 Unicode 문자 좌표로
대응시키고 엔진 span의 UTF-8 byte 범위와 연결한다. 대소문자·기호·Unicode 형태는
정규화하지 않는다. 원본 참조와 기존 exact/compact 점수는 그대로 둔다.

| 유형 | 해석 |
|---|---|
| 만·억·조 수 묶음 | 제44항에 따른 우선 개선 경계 |
| 수사 내부 | `십 이`, `열 두` 등의 발화 표기 차이; 일반 맞춤법 오류와 구분 |
| 번호·소수 자리 | 각 자리와 그룹을 끊는 선호; 자동 오류 판정 아님 |
| 단어 내부 | 유월·시월, 약어·관용형의 표기 검토 |
| 단위·접사 | 띄어쓰기 원칙과 순서 표현·접사·합성어 예외의 문맥 검토 |
| 줄바꿈·중복 공백 | 단어 경계와 문단/서식 경계 구분 |
| 나머지 경계 | 원문·조사·고유명사·보호 구간 등 추가 검토 |

유형은 자동 **검토 후보**다. 명사/조사 등을 완전히 분석하는 한국어 교정기는 아니며,
원문 토큰 사이의 애매한 경계는 미분류 검토로 남긴다. 매우 큰 수의 `구`는 숫자 9와
규모 이름이 겹치므로 자동으로 만 단위 경계라고 추정하지 않는다.
같은 문장이 여러 유형에 속할 수 있어 유형별 문장 수를 더하면 전체보다 커진다.
공백 외 차이가 있는 문장은 이 진단의 분모에 포함하지 않는다.

```sh
python3 benchmark/evaluators/spacing_audit.py \
  --report benchmark/generated/ko-release/reports/REPORT_ID \
  --out benchmark/generated/ko-release/spacing/REPORT_ID
```

출력 경로가 있으면 덮어쓰기를 거부한다. 보고서와 DB hash를 확인하고, 분석기 hash도
남긴다. 웹 `/ko-quality`의 ‘공백 차이의 종류’에서 경계 수·해당 문장 수·판단 기준·사례를
볼 수 있다. 사례는 기존 모달에서 원문·참조·출력 전체를 연다. 보고서 hash와 연결된
별도 진단 파일이며, 원래 평가 보고서를 수정하거나 점수에서 사례를 제외하지 않는다.
새 진단에는 `categories`별 같은 집계도 있으며 웹의 **공백 진단 범주**에서
나이·생년월일 등을 선택할 수 있다. 이 필드가 없는 과거 진단은 전체만 표시한다.

## 검증과 참조 이력

- 구현 전 작성한 `ko_spacing_v22.jsonl` 30건: 큰 수, 빈 묶음, 부호, 금액, 범위,
  전각 숫자, 소수, 번호, 영어, 원문 보존과 명시 별칭.
- `test_ko_spacing.py`: 두 분절 설정, 모든 2분할 byte 위치, 1 byte 입력과 난수 분할,
  Customer `space/compact` 정책. 결과 text/span/trace의 batch/stream 동일성 검사.
- 기존 출력 정책을 갱신한 참조는 [변경 전후 원장](audit/ko-spacing-policy-20260928.json)에 있다.
  자동 이관은 이전 엔진의 IR과 독립적인 숫자 묶음 계산만 이용했다. 쉼표 수량과
  명시 currency 제어 중 이관하지 못한 5건은 같은 규칙으로 별도 검토했다.
  후보 출력으로 참조를 생성하지 않았다. 외부 제공 참조는 변경하지 않았다.
- 출력 공백과 그로 인한 byte 좌표만 변할 수 있다. 의미 값·단위·입력 범위·규칙·언어,
  trace 선택 근거는 같아야 한다. trace 출력 좌표도 공백 제거 prefix가 같은 위치인지
  검사한다. declaration order는 선택 행과 같은 layer 안 상대 순서를 보존한다.
- 실제 보고 수치와 실행 명령은 [HANDOFF](HANDOFF.md)에 기록한다. Training 자료의
  참조 일치도이며 독립 held-out 정확도나 음성 품질 점수가 아니다.
