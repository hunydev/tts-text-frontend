# 일본어 TN 측정 (JSUT 읽기 비교)

2026-10-08, 프로젝트 오너 요청: 한국어·영어처럼 일본어도 참조 평가셋과 비교 TN으로 측정해, 나중에
상용화 가능 수준인지 판단할 수 있게 한다. 워크벤치 `/ja-quality`에서 결과와 사례를 본다.

## 참조와 비교 대상

- 숫자를 히라가나로 푼 공개 평가셋은 찾지 못했다(2026-10-08 조사). 가장 가까운 실제 참조는
  **JSUT BASIC5000**의 수동 히라가나 읽기다(`kana_level2`, sarulab-speech/jsut-label
  1978271c, **CC-BY-SA 4.0**). 5,000문장 중 아라비아 숫자가 있는 문장 253개, 한자 숫자만 있는
  문장 503개를 쓴다. 자료는 `benchmark/generated/ja-jsut/`에만 둔다(커밋하지 않음).
- 비교 TN은 둘 다 숫자를 **한자 숫자**로 쓴다(2024年 → 二千二十四年). 그래서 모든 시스템의 출력을
  같은 읽기기 **pyopenjtalk**(pyopenjtalk-plus, MIT)로 읽어 참조와 비교한다. 읽기기의 한자 오류는
  모두에게 같으므로 시스템 간 차이는 숫자 처리에서 나온다.
  - `raw`: pyopenjtalk 단독(원문을 그대로 읽음; 자체 숫자 확장 포함)
  - `wetext`: wetext 0.1.8 ja TN(WeTextProcessing FST, Apache-2.0) → 읽기기
  - `nemo`: nemo_text_processing 1.2.0 ja TN(Apache-2.0) → 읽기기. 전각 숫자를 읽지 못해
    전각 ASCII를 반각으로 바꿔 넣는다(다른 시스템은 원문 그대로).
  - `ours`: 이 엔진(ja-JP, speech; 숫자는 히라가나) → 읽기기
  - `ours-kata`: 같은 출력에서 숫자 구간만 가타카나로 바꿔 읽기기에 넣는다. 히라가나 숫자가
    앞뒤 글자와 붙어 읽기기가 잘못 끊는 경우(はちごう를 조사 は로 읽음)를 보기 위한 참고 값이다.
- 다른 후보: Apple PolyNorm-Bench ja-JP(540건, 27범주)는 **CC BY-NC-ND 4.0**이라 법무 확인 전에는
  쓰지 않는다. NeMo·WeText 테스트 파일(Apache-2.0)은 참조가 한자 숫자라 입력 자료로만 쓸 수 있다.

## 점수

- 양쪽을 같은 방식으로 정규화한다: NFKC, 가타카나, 장음(オウ·オオ·ウウ → オー, エイ → エー),
  じゅっ/じっ 동일 취급, 구두점·공백 제거.
- **숫자 구간 정확도(주 지표, 읽기기 없음):** 우리 출력에서 원문에 숫자가 있는 구간마다, 그 읽기가
  참조 읽기 안에 앞 구간 다음 순서로 있으면 맞음. 우리 숫자 읽기만 본다.
- **문장 일치·CER:** 읽기기를 거친 문장 전체 비교. 읽기기의 한자 오류가 섞인다.
- **조정 점수:** `benchmark/manifests/ja-jsut-review.json`의 참조 오류와 정책 차이 문장(7개)을 모든
  시스템에서 빼고 계산한다. 원 점수도 함께 보고한다.

## 자체 평가셋 ja-tn-eval-v1 (2026-10-08)

프로젝트 오너 요청으로 직접 만든 평가셋이다. 원문과 정답 읽기를 한 쌍으로 묶은 엔트리 1,250개, 채점 span 1,344개, 24개 범주로 이루어져 있다.
우리 TN에 맞춘 문장이 아니라 빈틈을 찾고 다른 TN과 같은 기준으로 비교하는 용도다. 형식과 채점 방식은 `benchmark/datasets/ja-tn-eval/README.md`에 있다.
채점 방식은 JSUT와 같다. 모든 출력을 pyopenjtalk로 읽어서, span의 허용 읽기 중 하나가 순서대로 나오면 맞은 것으로 센다.
`direct`는 리더 없이 우리 출력에 span 읽기가 그대로 들어 있는지 본다. 남은 한자를 VoxCPM2가 중국어로 읽을 위험까지 반영하므로 우리 기준으로는 이 값이 더 엄격하다.

고친 뒤(r9): 우리 91.5%(1,230/1,344), 숫자 가타카나 92.3%, direct 80.1%. date 범주는 95.7%, fraction 범주는 100%다.
남은 date 항목은 `1日から3日まで`(ついたち)처럼 문맥으로 갈리는 1日이다.
1. **버전·IP가 사라짐**: `v1.2.3`, `192.168.0.1` → 빈 출력. 버그.
2. **유니코드 기호 이름이 영어로 나옴**: `−`(minus sign), `〒`(postal mark), `★`, `→`, `°`, `©`, `™`, `≠`, `▲`, `No.`(number), `1st`(first), `etc.`(etcetera). ja 기호 읽기가 필요하다.
3. **라틴 대문자 한두 글자가 그대로 남음**: `A席`, `Sサイズ`, `Z世代`, `ビタミンC`, `A-12345`, `F-15`, `x=3`. 영문자를 가타카나로 읽어야 한다. 약어 단어 `NATO`, `JAXA`, `LINE`, `RAM`, `JPEG`은 철자로 읽힌다.
4. **조수사·접미 누락**: 箱(ひとはこ), 食, 世帯, 級, 次, 世, 週, 畳, 坪, カ所, 光年, 丁目, 番町, 強, 均, 対(いったいいち), 通り(とおり, 지금은 つうり), 何+조수사(なんぼん).
5. **수학·비율·점수**: `3:1`, `1:2`, `3-2で勝利`(たい), `10-4=6`, `12÷3`(= 뒤 숫자를 한 자리씩 읽음), `10²`, `3>2`.
6. **날짜 슬래시**: `3/15`, `5/3〜5/5`, `4/1(月)`가 분수로 읽힌다.
7. **전화·코드 문맥**: `110番`(ひゃくとおばん), `117`, `暗証番号は1234`, `認証コード`, `TEL.`, `FAX:`, `03（1234）5678`, `〒100-0001`, `3-12-5` 주소.
8. **기타**: `1足す1`(いっそくす), `1100キロ`(ひゃっキロ), `〇〇`(ぜろ), `−`, `￥` 전각 엔, `3割2分5厘`·`5分咲き`(ぶ), `F2.8`·`PM2.5`(two), `AM10:00`, `B1`·`2F` 층, `小6`·`中2`, `J1`·`F1`(ワン), `ツーアウト`, `ベスト4`.

이 목록은 계약을 먼저 쓰고 고칠 후보다. 정답을 우리 출력에 맞춰 고치지 않는다.


## 상용화 판단에 필요한 것

- JSUT는 일상 문장 위주라 단위·통화·범위·전화가 적다. 자체 평가셋 ja-tn-eval-v1(위)이 이 범주를 채우지만,
  상용화 판단의 기준으로 쓰려면 **원어민 검수**가 필요하다(지금은 작성자 1인, 검수 전). 입력은 NeMo·WeText 테스트
  입력(Apache-2.0)과 직접 만든 문장으로 채울 수 있다.
- 실제 대상 TTS(VoxCPM2)는 원문을 직접 읽으므로, 히라가나 숫자와 원문 숫자를 모델로 들어 보는
  A/B 비교가 함께 필요하다.

## 실행

```bash
~/venv-nemo/bin/python -I benchmark/evaluators/japanese_jsut.py \
  --library build/libtts_text_frontend.so --resources resources --tag NAME
```

`~/venv-nemo`에는 pyopenjtalk-plus, wetext, nemo_text_processing이 있다(VM 로컬). 결과는
`benchmark/generated/ja-jsut/summary-NAME.json`, `results-NAME.jsonl`에 쓰고 `/ja-quality`가 읽는다.
