# Finance and content scenario corpus

The v0.4 checkpoint below is retained as historical evidence. The v0.5 and v0.6 results
and promotion of known challenges into strict regressions are recorded at the end.

The current development priority is finance, followed by content creation. The
text frontend remains general purpose: domain resources may change policies,
while the universal core and language packs remain reusable. Evaluation is
limited to normalized text, semantic/language metadata, and batch/stream parity.

## Where these examples come from

These are **original synthetic scenarios authored for this repository**. They
contain no customer records, production traffic, copied scripts, or externally
annotated evaluation data. An agent authored the input and reference text from
the intended reading policies before executing the frozen baseline on them.
They have not received independent human linguistic review. Passing them is a
regression result, not a measurement of real-world financial or language accuracy.

The reference strings are stored explicitly in JSONL. They are not generated by
running the frontend. Existing policy choices are retained: Korean number/unit
spacing, `유 월` and `시 월`, 24-hour clock readings, decimal digit order, and the
default range separator `다시`. A financial application's policy may differ and
should be agreed upon before adopting these references.

| File | Purpose | Cases |
| --- | --- | ---: |
| [`domain_cases.jsonl`](../tests/evaluation/domain_cases.jsonl) | Development regressions used to guide and verify this iteration | 60 |
| [`challenge_cases.jsonl`](../tests/evaluation/challenge_cases.jsonl) | Additional desired behaviors and ambiguous cases, first executed after the implementation work | 15 |

The development set contains 30 finance, 18 content, and 12 technical/customer
cases. It adds 33 explicit span checks. These proportions reflect the current
product priorities; they are not weights estimated from a production workload.

### Development categories

- **Finance:** compound and signed won amounts, decimal scale arithmetic,
  rates, fractions, notices, deadlines, contacts, English invoices, malformed
  amounts, and explicit domain/customer reference-number policies.
- **Content:** product introductions, borrowed noun phrases, embedded English
  clauses, ordinal titles, video durations, prices, ingredient quantities,
  temperature, and English promotional text.
- **Technical/customer:** mixed terminology, versions, addresses, links, email,
  appointments, phone numbers, and bilingual directions.

The reference-number cases explicitly load the existing finance/customer range
policy. They do not imply that the engine identifies bank accounts from a label
or knows real account-number validation rules.

| --- | ---: | ---: |

The candidate result measures the selected development cases used during this
iteration. It demonstrates regression fixes; it does not establish 100% accuracy
on arbitrary finance notices or content scripts. All 33 span assertions pass,
including the six compound-amount semantic spans.

The text-only total concealed a specific semantic defect. For example,
`1억2천3백만원` happened to produce the expected concatenated text in the baseline,
but it was split into several semantic items. The reference requires one
`CURRENCY` span with value `123000000` and unit `KRW`. This checks that arithmetic
and classification are correct before downstream rendering.

Other baseline failures included a space left inside a compound amount,
partial readings of malformed scale sequences, missing loanword entries, and
English clause endings incorrectly switched to Korean pronunciation.

For a candidate run:

```sh
python3 tools/evaluation/evaluate.py --ttf build/ttf --resources resources \
  --corpus tests/evaluation/domain_cases.jsonl \
  --output-dir artifacts/domain-candidate
```

The evaluator uses chunk sizes 1, 7, and 64 bytes by default. It also compares
batch output and checks UTF-8 span coverage. Keep both completed JSON reports and
compare the same frozen reference file. Native tests separately exercise shorter
segment targets and additional stream partitions.

## Challenge set and interpretation

The 15 challenge references were written before their first execution. Their
SHA-256 at authoring was:

```text
4ae71edddfde98aa4e38c8cbeb83ad1d0b3f1d4fdeef1ce6e297ffa4c62bdf10
```

They include desirable behavior beyond this iteration's promised coverage:
labelled account/reference identifiers, finance-specific units, scientific
notation, decimal ranges, a longer compound amount, English contractions,
hyphenated borrowed phrases, unseen vocabulary, an unquoted English title,
AM/PM, and explicit code/path preservation. Each case records its intended
policy or ambiguity in `notes`. In particular, markup is outside the current
plain-text contract, and an unquoted title may require application-supplied
language metadata.

This is a small, author-selected challenge set. It is not a statistically
representative holdout, and the developers can see the file. Its initial results
must be reported separately from the development gate. Failures are useful
backlog evidence; they must not be hidden by replacing the reference with the
current output or by claiming unsupported policies already exist.

```sh
python3 tools/evaluation/evaluate.py --ttf build/ttf --resources resources \
  --corpus tests/evaluation/challenge_cases.jsonl \
  --output-dir artifacts/challenge-candidate
```

A mismatch returns status 1 while still writing the full report. A malformed
corpus/protocol or execution failure returns status 2 and is an infrastructure
error, which must remain distinguishable from an expected challenge mismatch.
Do not use an unconditional `|| true` to suppress either kind of failure.

Once a challenge failure is used to guide an implementation change, that case is
a development regression for that work. It must no longer be described as
untouched evaluation evidence. Record policy changes explicitly, keep the old
reference/report provenance, and obtain additional examples for later review.

## First challenge execution after implementation

The reference file was unchanged. Initial execution on the frozen baseline and
v0.4.0 candidate produced:

| Metric | Baseline | Candidate |
| --- | ---: | ---: |
| Exact/overall passing cases | 1 / 15 | 3 / 15 |
| Remaining failures | 14 | 12 |
| Character edit distance / reference characters | 109 / 405 | 112 / 405 |
| Character error rate | 26.9136% | 27.6543% |
| Batch/stream divergence | 0 | 0 |

Two cases improved: the final word of an English contraction clause remains
English, and a longer compound amount receives the correct unit spacing. The
ambiguous unquoted title `제목은 The 1st day입니다.` became further from its
English-preserving reference (3 → 11 character edits): noun-phrase routing now
localizes all three words. No previously passing case failed, but that increased
text error is still a regression signal. The comparison tool reports both kinds
of regression rather than hiding worsening behind the passing-case count.

The 12 failures cover account/reference identifiers, `%p` and `bp` units,
scientific notation, decimal ranges, hyphenated loanwords, an unknown word,
ambiguous English titles, AM/PM, code paths and markup. These outcomes have not
been used to tune this release. Full evidence is in
`artifacts/challenge-candidate-0.4.0/report.json` and
`artifacts/challenge-comparison-0.4.0-final/comparison.json`; CI republishes the
current challenge report alongside the strict development results.

The low challenge score is deliberate coverage evidence for selected hard or
unsupported cases, not a random-sample estimate of production accuracy. Its
failures must remain visible in release reporting. The next development phase
should move adopted financial cases into strict regression gates after agreeing
identifier and unit policy; leave other unsupported forms explicitly documented.

A compact, versioned copy of the measured summaries and changed/failing outputs
is committed as [0.4.0 text evidence](evidence/0.4.0-text-results.json). It records
reference and executable hashes; the full reports additionally retain span streams.

## What stronger validation needs

1. Human review of reference readings, particularly ambiguous finance units,
   identifier policies, title language, and foreign-name pronunciations.
2. Representative, authorized, de-identified customer sentences with agreed
   expected text and domain settings.
3. Error categories for wrong numerical value, dropped text, wrong language
   routing, pronunciation spelling, unsupported syntax, and harmless policy
   differences. Aggregate character error alone can conceal a serious value error.
4. Separate development and independently maintained evaluation corpora, with
   documented provenance and policy versions.
5. Continued adversarial checks for invalid amounts, overflow, UTF-8 boundaries,
   and stream splits through multi-token semantic constructions.

No synthesis backend, generated audio, listening score, or acoustic comparison
is part of these acceptance criteria.

## v0.5 advanced regression checkpoint

The new `advanced_cases.jsonl` contains 30 original synthetic development cases:
13 adopted from the unchanged challenge file, plus 17 explicit additional
references. They exercise explicit identifier cues/zeros, rate units, exponent
amounts, decimal ranges, title context, loanwords and AM/PM. This is a development
set used to guide implementation, with no independent human annotation.

References were fixed before the first execution on the frozen v0.4 binary and
resources (commit `493f966`). Their SHA-256 is:

```text
5c88870b780e2a10442dc159a1815af8a33d72acd0b39c6d4e0e554187b048e0
```

| Same fixed references | v0.4 | v0.5 |
| --- | ---: | ---: |
| Advanced strict cases, text + metadata + parity | 8/30 | 30/30 |
| Advanced character edit distance / reference characters | 240/775 | 0/775 |
| Original 60 scenario cases | 60/60 | 60/60 |
| Unchanged 15 challenge cases | 3/15 | 13/15 |

The challenge file is kept to show historical progress, but 13 of its references
are now training/development material for this engineering iteration. It cannot
be presented as an unseen holdout. The two remaining failures are HTML/code and
file-path treatment; the plain-text frontend still verbalizes parts of them.
The new `quasar` spelling is an explicit lexicon entry, not a solved unknown-word
phonetic rule. [Financial text contracts](financial-text.md) state the supported
forms and numeric bounds.

CTest and CI require the advanced corpus to pass. CI also publishes the unchanged
advisory challenge report, including remaining failures. Compact metrics, hashes
and changed outputs are committed in `docs/evidence/0.5.0-text-results.json`.

## v0.6 literal-source checkpoint

The separate 40-case `protected_cases.jsonl` was frozen before execution on v0.5
and the v0.6 candidate. It covers code/markup, paths, context isolation, neighboring
finance/content normalization and negative guards. Text+metadata+parity acceptance
improves from 4/40 to 40/40 (text-only 8/40 to 40/40).

The existing 60 scenario and 30 advanced cases continue to pass. The original
15-case challenge file now passes 15/15: its final two code/path references are
also covered by the new strict suite. All these challenge cases are now known
development cases. This records regression progress without implying unseen
accuracy or complete HTML/Markdown support. [Protected text contracts](protected-text.md)
contain detailed scope, provenance and remaining limits.
